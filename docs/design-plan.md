# SnakeLab 设计计划

版本：0.1 · 2026-10-05 · 状态：待评审，尚未实现。

## 1. 目标与首版范围

让玩家能玩，让学习者能看懂决策，让实验者能在相同规则下比较策略。首版先证明规则正确、操作顺畅及基础算法可复现，再增加训练。初期使用静态网页、本地计算和本地存储；账号、云训练、联网对战不进入首版范围。

建议首版默认 12×12 无障碍矩形棋盘、单蛇、单食物、不穿墙，初始长度 3。另用 8×8 作为训练小场景。棋盘、初始化方案与规则版本写入实验配置，训练与竞技不可暗中切换规则。此处尺寸和预算均是评审起点。

## 2. 规则与确定性核心

核心不依赖 DOM、PixiJS、React 或训练框架。计划接口如下（接口意图，不是已存在 API）：

| 接口 | 约定 |
| --- | --- |
| `reset(seed, config)` | 创建完整初态，重置环境 PRNG，返回观察与规则元数据 |
| `step(action)` | 推进恰好一步，返回观察、事件、`terminated`、`truncated` 与原因 |
| `observe()` | 只读观察，不推进状态或随机数；策略不得修改核心状态 |
| `snapshot()/restore()` | 保存/恢复蛇体顺序、食物、方向、计数器、PRNG 状态与版本 |

核心采用四个绝对方向；策略适配层可把相对的左转/直行/右转映射到绝对动作。反向动作统一判为非法并保持前向移动，记录非法输入；手动输入缓冲每步最多接受一次方向变更。碰撞、非法动作与预算超时是不同事件。

一步顺序：解析动作 → 计算新蛇头和是否吃食 → 判断墙体及身体碰撞 → 移动/增长 → 在空格中用确定性 PRNG 均匀生成食物 → 检查结束。未增长时尾格即将释放，允许进入该格；增长时尾部保留。占满所有可用格时胜利，不再生成食物。终局后重复 step 返回稳定终态，不继续变更随机数。

`terminated` 表示撞墙/撞身/填满等规则终局；`truncated` 表示实验步数、无进展或时间预算耗尽，独立统计。所有模式采用同一可配置规则；手动娱乐可不启用实验截断，但此类结果不并入正式比较。

环境、策略探索、网络初始化和 replay 采样使用分离的随机流。固定种子和动作序列应产生一致状态哈希；GPU 训练只追求记录充分和统计可复现，不承诺跨设备逐位一致。

## 3. 架构与技术选择

建议 TypeScript + Vite + PixiJS + React，待小型技术验证后定案。PixiJS 管理一个渲染器和多个棋盘容器，React 管理表单、统计与可访问控件；棋盘逐步状态不经 React 逐格重绘。[PixiJS 官方 Application 文档](https://pixijs.com/8.x/guides/components/application)说明其渲染及 ticker 机制。

计划职责（下列目录尚未创建）：

| 模块 | 责任 |
| --- | --- |
| `src/core` | 状态、PRNG、碰撞、食物、快照、规则版本 |
| `src/agents` | 统一决策接口、策略参数、可选 debugInfo |
| `src/experiments` | 种子集、预算、调度、指标与结果导出 |
| `src/workers` | 无图仿真任务、训练任务、消息协议、取消 |
| `src/training` | DQN/GA 更新逻辑与检查点 |
| `src/render` / `src/ui` | 棋盘绘图与操作面板 |
| `src/storage` | 回放、模型与实验数据的版本校验 |

Agent 输入为只读 observation、配置、种子流与预算，输出 action 和可选 `debugInfo`（路径、已搜索格、安全检查原因）。模型观察是核心观察的版本化编码，不允许通过未来食物或环境 PRNG 偷看答案。

仿真按 step 数推进；观看模式由调度器决定每秒步数，渲染按屏幕刷新率采样。训练不依赖 FPS，不必每步绘图。初始建议统计刷新 5 Hz、可视棋盘最多 4 个，显示刷新率只是 UI 参数。

Worker 池初始最多 2 个仿真 Worker，训练先用 1 个专用 Worker，检测能力后按预算调节；消息带 jobId、配置版本和序号，过期快照丢弃。任务分块并让出事件循环，暂停在块边界确认，取消清理张量和缓存。传输批量指标及选定棋盘快照，避免每步复制全部棋盘。线程数量不是越多越快，移动设备须降并发。

Phaser 可作为场景、音效、Tween 需求增长后的备选；其 [Game/Scene 系统](https://docs.phaser.io/phaser/concepts/game)更完整，但 `HEADLESS` 仅表示无渲染配置，不能据此认定可直接在 Node 中训练。无图实验始终运行独立核心。

### 3.1 浏览器训练后端

核查日期 2026-10-05，依据见[参考文档](references.md)。

| 候选 | 本项目用途 | 决策前验证 |
| --- | --- | --- |
| TensorFlow.js | 首选训练候选，Layers/Core API 可进行梯度更新 | DQN 前向、梯度、优化器、保存恢复、Worker 内运行及泄漏检查 |
| TF.js WebGL | 浏览器训练优先验证后端 | 与 PixiJS 的 GPU 争用、精度、上下文丢失、移动端温度和耗电 |
| TF.js CPU / WASM | CPU 为小模型正确性回退；WASM 为可选加速实验 | WASM 文档优先推理，必须确认所需训练/梯度算子，不能仅凭前向通过就启用训练 |
| WebGPU | 后续性能候选 | 锁定所选库版本，逐项测浏览器/Worker/算子/数值稳定性；不可把渲染支持视为训练支持 |
| ONNX Runtime Web | 后期导入模型推理 | 模型算子、形状、后端支持与输出一致性；官方有训练示例，但本项目不将其作为常规 DQN 训练主后端 |

先以小 MLP 完成一次真实更新和检查点恢复，再决定后端。分别测无绘图、单棋盘、多棋盘时的样本吞吐与 UI 延迟；降低训练批频或切换已验证后端。WASM 线程/隔离头与部署条件单独验证；无法支持时降为单线程。使用显式张量释放、异步读取，监控内存是否随训练持续增长。

版本选择原则：从稳定发行版中选互相兼容的 TypeScript/Vite/React/PixiJS/TF.js 组合；核对 Node 要求及浏览器目标；锁定精确依赖和 lockfile，记录后端及设备矩阵。以最小技术验证通过作为选择依据，不追逐最新版本。本次不安装这些依赖。

## 4. 自动游戏策略

| 策略 | 计划实现与价值 | 边界 |
| --- | --- | --- |
| Random / Legal Random | 原始随机作失败对照；合法随机过滤立即碰撞，种子化选择 | 无合法动作时按固定规则结束；长期可达性未保证 |
| Greedy | 向食物的曼哈顿距离优先，平局固定顺序；可选安全过滤作为独立变体 | 贪心会自陷，带过滤与不带过滤分开报告 |
| BFS / A* | BFS 为单位代价基线；A* 使用与非环绕规则一致的启发式，维护 gScore 并允许更优路径更新 | 搜索预算有上限，静态路径不等于未来可执行路径 |
| Hamiltonian 环 | 按预先构造的环移动，作为满足条件时的安全基线 | 无障碍矩形、宽高均大于 1 且至少一边为偶数；蛇体沿环连续初始化、朝环方向移动 |

BFS/A* 每步重新规划。候选路径需按真实规则模拟整条蛇，包括尾部释放、吃食后增长；再检查模拟终点到尾部的可达性及 flood-fill 可用空间。搜索可先用静态占用图生成候选，再作动态验证；后续可研究时空状态搜索。尾部可达和空间足够只是启发式，不能承诺必胜。失败时回退到有空间检查的合法动作，预算耗尽记录 fallback 和原因，不无限搜索。

Hamiltonian 首版不走捷径，先验证环覆盖、相邻性、蛇体顺序与碰撞不变量。不满足条件时 UI 标记策略不可用；障碍或奇数×奇数棋盘不能套用该构造。将 Hamiltonian 特殊初始化与其他策略相同初始化的比赛分组，避免比较条件不同。

DFS、Dijkstra 可作为教学扩展；无权图上 Dijkstra 不作为优于 BFS 的默认选择。Double DQN、Dueling 等在基线稳定后再研究。

## 5. DQN 浏览器训练计划

先固定 8×8 场景与小型 MLP，输出相对三动作 Q 值。初版观察为全盘头/身体/食物通道、身体顺序归一化通道，加方向 one-hot；身体顺序用于表达尾部未来释放。编码、输入形状、方向和动作约定写入模型版本。局部危险/距离特征可做后续消融，不与全盘模型混成同一结果。

建议起始实验配置：两层 64 单元 ReLU、Adam 学习率 0.001、gamma 0.99、Huber loss、batch 32、replay 20,000 条、预热 1,000 步、每 4 环境步更新一次、每 1,000 优化步同步 target network。全部是待调参起点，预先估算 replay 字节数并使用紧凑数组。

每条经验存储 `(obs, action, reward, nextObs, terminated, truncated)`。TD target 用冻结 target network；真实终局不 bootstrap。时间/无进展截断的处理必须在实验配置中声明：建议外部步数限制保留 final observation 并 bootstrap，环境定义的失败终局不 bootstrap；禁止把 reset 后首帧作为 nextObs。

奖励初案：吃食 +1，碰撞 -1，普通步 -0.001，填满额外 +1；无进展截断不冒充碰撞。不先加入靠近食物奖励，以减少绕圈刷分；如后续加 shaping，另建 rewardVersion 并做消融。统一每局上限 5,000 步和连续无食物 500 步，参数随棋盘调整须形成新协议。

训练 epsilon 按环境样本数从 1.0 线性降到 0.05（起始建议 50,000 步），不用 FPS 或墙钟衰减。评估冻结权重、epsilon=0、固定平局规则；如要评估随机策略，单列其探索参数。训练种子、调参验证种子和最终测试种子分开，正式测试集不参与选模型。

每 10,000 样本在验证集评估，记录得分分布、失败率及耗时；至少 3 个独立训练种子观察波动，不以单次最好结果宣布提升。初始交互预算建议 100,000 样本或 5 分钟先到即停，用户可显式延长。训练效果是实验目标，不保证胜过搜索策略。

检查点包含在线/目标权重、优化器状态、网络/观察/奖励版本、步数、epsilon、随机流和配置；可选完整 replay 与环境快照。只保存权重称为推理导出或 warm start，不声称精确续训。恢复应检查形状和版本，比较加载前后固定观察的输出；完整恢复再核对计数器与 replay。

## 6. GA / 神经进化计划

先以小型策略网络权重为染色体，使用与 DQN 相同的观察和动作适配；训练时不需要梯度。每代所有个体共享训练种子子集，减少运气干扰，并用独立验证集选冠军。

初始建议种群 32、每个体 5 个种子、精英 2、锦标赛选择、均匀交叉、逐参数高斯变异（概率 0.05、标准差 0.1）。适应度优先平均填充率，再结合失败率和吃食效率；生存步数只作有上限的平局项，防止空转获益。各权重、选择规则与 tie-break 写入配置，保留每代分布而非只展示冠军。

预算同时限制总环境样本、每局步数、代数与墙钟。初始最多 50 代且 5 分钟先到停止，不要求默认预算内收敛。Worker 分配个体评估，记录完成索引和随机流；暂停/取消在小任务边界生效，保存种群、适应度、代数、随机数状态和未完成任务。导出冠军后进入冻结的统一评估流程。两个指定参考项目均未见 GA 路线，此部分为新增设计。

## 7. 模式与交互

手动模式提供焦点明确的棋盘、方向键/WASD、触控方向按钮和暂停/重开；输入框获取焦点时不拦截方向键。失去页面可见性时默认暂停游戏及训练，恢复需明确提示，避免后台节流改变用户预期。

AI 模式显示策略、种子、步数、速度及终局原因，支持单步和可选路径/搜索格叠层。多策略竞技是多个独立棋盘，非同一棋盘互撞；使用相同地图、初态和种子集。同种子保证可重复，不保证不同蛇轨迹吃到相同坐标序列，因为合法空格会不同；若需固定食物脚本，另设可执行性处理协议。

批量模式只展示汇总和抽样棋盘，导出 JSON/CSV。训练实验室展示样本数、更新次数、epsilon、验证曲线、预算和停止原因。回放记录配置、核心版本、seed、动作、状态哈希及必要快照，能重现推理结果而无需重跑训练。

移动端优先单棋盘，控制区置于下方，训练默认低预算；用文字和图例补充颜色，不仅凭颜色区分蛇头、路径和失败。后期障碍模式需重新定义 Hamiltonian 可用性、搜索预算与基准分组。

## 8. 公平比较与数据记录

预先固定协议 ID、地图/初始化、种子清单、终止/截断、决策预算与 fallback。起步每策略使用 100 个共同测试种子，按种子配对比较；训练策略另报告训练成本与多个训练随机种子的离散度。训练与评估数据分开存储。

| 指标 | 定义 |
| --- | --- |
| 得分/食物数 | 每局吃到的食物数量 |
| 填充率/成功率 | 蛇长 ÷ 可用格数；填满的局数比例 |
| 失败与截断 | 碰撞率、无进展/步数/墙钟截断率分别报告 |
| 步数/效率 | 每局步数、每食物步数；零食物单列，不做除零 |
| 决策成本 | 预热后的 p50/p95 延迟、超时次数、搜索展开节点数 |
| 训练成本 | 环境样本、梯度更新/代数、墙钟、峰值可测内存 |
| 系统体验 | 有/无渲染的吞吐、主线程响应、取消耗时 |

建议搜索上限 10,000 展开节点并配合 20 ms 决策预算，按设备验证后固定；超时采用统一 fallback 并统计。比较中既报告相同步数预算的算法质量，也报告相同设备墙钟预算的效率，不把二者混为一个排名。汇报均值、中位数、分位数和配对差值/置信区间；记录浏览器、硬件、依赖、后端、提交 SHA、预热与渲染开关。尚无本项目实验结果。

## 9. 资源、存储与模型输入

预算预设：桌面 2 个仿真 Worker、1 个训练 Worker，移动端降至单任务；模型导入建议上限 10 MB，棋盘 64×64 封顶，replay 与日志分别设字节上限。均需首轮实测修订。UI 在启动前显示预计工作量，并支持取消；内存/后端异常保存可用摘要后停止。

模型导入仅接受声明的 JSON/权重二进制等数据格式，验证 schema、大小、形状、dtype、有限数值、允许层/算子及观察版本；不执行上传 JS、任意自定义层代码或模型内远程引用。回放和实验结果同样校验长度和版本。优先 IndexedDB 保存检查点，文件导出作为备份；存储不足提示用户选择导出或清理，不静默丢失实验。

所有阶段目前均为“计划”，下表是未来验收任务，不代表测试已通过。

| 阶段 | 交付 | 可判定验收条件 |
| --- | --- | --- |
| P0 设计评审（本次） | README、设计、参考依据 | 路径有效、现状明确、技术与算法边界有出处 |
| P1 MVP | 纯核心、手动、Random/Greedy/BFS/A*、基本观看 | 覆盖尾格释放、增长、碰撞、满盘、反向输入、终局稳定；同 seed+动作哈希一致；键盘/触控与暂停实测 |

| P3 DQN | 后端验证、训练/eval、检查点 | 小 batch 确有有限梯度和权重更新；target 同步正确；终止/截断 target 测试；eval 不更新权重且无探索；加载输出一致；连续训练内存不持续增长 |

实现阶段建议 Vitest 检查核心与算法，Playwright 检查浏览器流程；性能在明确设备矩阵上测量。初始体验目标是桌面四棋盘观看时操作响应 p95 <100 ms，训练取消确认 <1 s；属于待实测目标。搜索/训练数值检查失败时保持在当前阶段，不先扩展模型。

## 11. 需要评估的决策

1. 首版 12×12 游戏、8×8 训练的组合是否合适，还是统一棋盘以降低比较复杂度？
2. 优先接受 PixiJS + React 的分工，还是游戏效果需求足以采用 Phaser？
3. 第一轮研究先比较安全搜索与 Hamiltonian，还是更早验证 DQN 小规模训练？建议先完成 P2 的协议和回放。
4. 目标设备以桌面为主还是手机也要训练？这决定默认预算与后端选择。
